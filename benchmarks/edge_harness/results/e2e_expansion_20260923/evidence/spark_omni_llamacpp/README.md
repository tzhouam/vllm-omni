# Spark GGUF through Omni on native Windows CPU and Radeon 890M

This is a **scoped complete-request text path** for one pinned Spark-X2.5-1.7B Q4_K_M GGUF. The new `external.llamacpp.text.v1` client runs inside Omni `StageRuntime`/`StagePool`; a separate public `AsyncOmni.generate` request also passed with a real Spark HF config directory and the registered `spark2_5_gguf_text` pipeline. llama.cpp owns weights, KV and internal sampling. Omni owns the process lifetime, one-slot admission, declared 4 GiB host-RAM reservation, request identity, terminal text event, acknowledgement and cancellation cleanup. It uses the existing complete-request graph control path, not an ONNX graph. At the time of this profile, incremental token streaming, restart after cancelling an active request, model-wide quality and thermal qualification were open; the later fresh-stage restart result is linked below.

The pinned GGUF is [XHToken/Spark-X2.5-1.7B-GGUF](https://huggingface.co/XHToken/Spark-X2.5-1.7B-GGUF/tree/1f7fa33b1245c14730da39e125714ad3a327901b) revision `1f7fa33b1245c14730da39e125714ad3a327901b`, file `Spark-X2.5-1.7B-Q4_K_M.gguf` (1,107,457,856 bytes; SHA-256 `902bde2522394954ac17821b3e5fd0df02defbc6944f122253f2580acf0503f4`). The executable is llama.cpp [b11124](https://github.com/ggml-org/llama.cpp/releases/tag/b11124), build commit `1a679828f`, `llama-server.exe` SHA-256 `9ffc5919acb4cb43c7be5f3053b59014cce70a87d3a801fcad49c4f459984f52`. The artifact remains in local model storage. The model and executable hashes are checked before launch. The source/checkpoint and earlier standalone tests are in the [prior record](../spark_radeon890m_llamacpp/README.md).

A later [2026-09-24 recovery experiment](../../../e2e_expansion_20260924/evidence/spark_omni_windows_restart/README.md)
confirmed that the server had started the cancellation workload on both CPU
and Radeon 890M, then a fresh Omni stage using the same artifact answered
correctly with a new worker generation and no stale output or reservation.
The original profiles below remain separate measurements.

Host: Windows 11 build 26200, Ryzen AI 9 HX 370, Radeon 890M driver `32.0.22018.6001`, Performance power scheme. An RTX 5090 Laptop GPU was installed but was not selected. The native Python environment was vLLM 0.29.0 with the current Omni source. The server used one slot, 4,096 context tokens, FP16 KV, temperature zero, reasoning off, `--fit off`, `--cache-ram 0`, and per-request `cache_prompt=false`. The backend tokenizes each prompt before submission and refuses a prompt plus maximum generation bound that exceeds the declared context. It refuses a partial generation `finish_reason`. The 4 GiB admission includes the 1.11 GB model plus declared 2 GiB KV/workspace/transfer/headroom; this is an explicit bound, **not** a measured loading or shared GPU-memory peak.

The profile input is the fixed 120-item synthetic inventory and asks for district 73's code (`1511`); the server reports 2,463 prompt and 5 completion tokens. Both backends also answered the short `Paris` question. The [CPU JSON](omni_llamacpp_cpu_tokenbound_20260923.json) and [Radeon JSON](omni_llamacpp_radeon_tokenbound_20260923.json) retain every request wall time, output, usage, stage event, placement plan and ledger snapshot. Their [CPU server log](omni_llamacpp_cpu_tokenbound_20260923.log) and [Radeon server log](omni_llamacpp_radeon_tokenbound_20260923.log) show the hardware and real load. Timings include Omni stage submission, local HTTP and response delivery but exclude startup; they do not measure TTFT because this adapter returns complete requests. These runs are distinct from the earlier standalone 6.65/6.86 s CPU and 2.18/2.20 s Radeon profiles, so differences should not be attributed solely to Omni overhead.

The Radeon run rejected an over-context prompt before generation, then answered `Paris` correctly. Both runs cancelled a live request, observed no stale output, terminated the owned server and released all ledger reservations without quarantine. A [final one-request Radeon smoke](omni_llamacpp_radeon_final_smoke_20260923.json) repeated the context and abort checks after the cleanup-path hardening. This proves drain and fencing for that path, not automatic backend restart or ability to continue serving after a cancelled in-flight request. An intentionally wrong expected device name was [refused](omni_llamacpp_wrong_device_20260923.json); its [log](omni_llamacpp_wrong_device_20260923.log) identifies the actual Radeon and its Vulkan1 model buffer. The [Radeon public entrypoint JSON](omni_llamacpp_radeon_public_realconfig_20260923.json) and [CPU public entrypoint JSON](omni_llamacpp_cpu_public_realconfig_20260923.json) each record `AsyncOmni.generate` returning `Paris` and a terminal text event using a real Spark HF config directory for pipeline resolution; the GGUF, rather than the HF BF16 weights, was the executed artifact.

Reproduce with the [stage profile script](../../../../experiments/probe_omni_llamacpp_spark.py) or [public entrypoint script](../../../../experiments/probe_omni_llamacpp_entrypoint.py) from the native Windows environment. Set `PYTHONPATH` to this checkout, `PYTHONUTF8=1`, and `VLLM_ENABLE_V1_MULTIPROCESSING=0`. Supply the pinned `--model-file`, `--server-bin`, their SHA-256 arguments, `--device cpu` or `--device Vulkan1 --expected-device-name 'AMD Radeon(TM) 890M Graphics'`, and output paths. Use `--warmups 1 --repeats 20 --context-check --abort-check` for the Radeon stage profile; the CPU profile used the same warmup/repeats and abort check. The public probe additionally accepts `--model-config-dir` for the real Spark HF config. Raw driver logs retain the exact environment setup and failures.

The acceptance boundary of these original runs remains two named text inputs, one repeated serial profile, a single local worker and one short public API request. The later linked experiment covers one fresh-stage restart after confirmed server-start cancellation per device. Broad text quality, concurrency, load peak, device-memory attribution, token streaming and sustained power/thermal behavior remain unverified; the other device × model cells are unchanged by this backend.
