# MiniCPM-o WSL CUDA image path: shutdown retest

This is a scoped real-weight, three-stage Omni image-to-text+speech run on the HX370 laptop with RTX 5090 Laptop GPU under WSL2. It uses the same pinned MiniCPM-o 4.5 checkpoint, red-square input and deploy configuration as the [earlier 20-request image profile](../minicpmo_cuda_image_profile20/README.md). The runtime reports vLLM 0.29.0, Torch 2.13.0+cu130 and CUDA device 0. The raw [20-request report](profile20/report.json), [per-request JSONL](profile20/report.jsonl) and [runtime log](profile20/run.log) retain the input/config hashes, environment, memory samples, outputs and shutdown sequence. This is a separate serial run; timing differences are not a paired performance comparison.

One warmup plus 20 measured image requests each returned the same correct red-square description and 124,800 nonzero audio samples (5.2 s at 24 kHz). Nearest-rank complete-request wall p50/p95 was **15.377/15.773 s**, excluding 89.740 s startup. The single-request [smoke report](report.json) and [log](run.log) also passed. In both runs, stage 0, stage 1 and stage 2 retired normally: no forced worker kill and no `resource_tracker` shared-memory warning appeared. The smoke counted 69 preexisting `/dev/shm/0_*` lockfiles both before and after; no lockfile or shared-memory segment for the smoke request remained. The 20-request run likewise left no request-specific segment after process exit.

The previous 20-request run emitted 21 shared-memory warnings and force-killed stage 0. A diagnostic with only a longer head-side shutdown grace [still left a resource-tracker warning](../minicpmo_cuda_shutdown_grace/report.json). The source change closes the scheduler-owned chunk transfer adapter and joins its background threads before connector close, then allows the stage client 15 seconds to retire its worker. That sequence removes the observed exit-time warning on this CUDA workload.

This does **not** prove per-request resource release during a long-lived engine. Sampling `/dev/shm` during the new run found roughly one 116-byte terminal-marker segment per completed request pending until shutdown (2 after two requests, 5 after five, 7 after seven, 12 after twelve and 18 while request 17 was active). The marker lifetime and boundedness under sustained/concurrent load remain open. Text-to-speech alignment, broader image quality, playback and power/thermal behavior also remain unqualified.

**Later result:** the [sender-role retest](../minicpmo_cuda_marker_fix/README.md) removed the observed per-request stage-0 marker accumulation in another 20-request serial image run. The transient marker observations above remain the raw result for this earlier checkout; concurrent and sustained bounds are still open.
