# MiniCPM-o WSL CPU BF16 image path: shutdown retest

The current three-stage Omni BF16/vLLM CPU path ran the pinned MiniCPM-o 4.5 checkpoint on the HX370 WSL guest with `VLLM_TARGET_DEVICE=cpu`, no visible CUDA device, `VLLM_CPU_KVCACHE_SPACE=1`, and eight OpenMP/MKL threads. The installed vLLM wheel reports 0.28.0 against Omni 0.29 source. The [production report](report.json), [JSONL](report.jsonl), and [runtime log](run.log) retain the config/input hashes, sampled memory, exact text, waveform statistics, and shutdown events. The workload is **one** synthetic red-square image → text+speech request after 97.424 s startup; it is not a 20-request or speech-quality qualification.

The request described the red square on white and returned 124,800 nonzero audio samples (5.2 s at 24 kHz) in 50.743 s complete-request wall time. Sampled WSL memory used peaked at 31,535,763,456 bytes and swap used at 5,549,830,144 bytes. The thinker stage retired about 17 seconds after SIGTERM, followed by both remaining stages; the profiler exited 0 with no forced worker kill, orchestrator timeout, `resource_tracker` warning or abort. No CUDA placement is claimed.

The lifecycle history matters. An initial [15-second stage-grace attempt](../minicpmo_cpu_shutdown_fix/run.log) produced correct output but force-killed stage 0; the fixed 30-second outer orchestrator join then expired while later stages were still closing, and the process aborted. A [stage-count-aware outer budget](../minicpmo_cpu_shutdown_budget/run.log) removed the parent abort but still force-killed stage 0 after 15 seconds. A diagnostic [30-second per-stage grace](../minicpmo_cpu_shutdown_grace30/run.log) let all stages retire without a force kill. The production run above confirms that the device-specific 30-second CPU grace and a 105-second three-client outer join work together. These serial attempts had changing cache/swap conditions and are not paired latency comparisons.

The older WSL CPU GGUF route has a separate 20-request combined image+audio profile. This BF16 run validates one image input only. General image/audio quality, speech meaning and alignment, sustained concurrency, loading peak, and power/thermal behavior remain open. The high shared-RAM and swap demand also limits this exact placement on a 30 GiB WSL guest.
