# Spark 4B BF16 CUDA batch-slot reference

**Disposition (2026-09-25): the 2026-09-22 Omni batch-dependent greedy token variants reproduce in standalone vLLM with the same checkpoint and engine plan.** This rules out Omni's event transport as the source of those particular differences; it does not prove which CUDA/model operation causes them or qualify their text quality. The default Spark gate path was left unchanged. An opt-in FP32 gate projection removes the medium-prompt variants in this bounded probe but does not remove the long-prompt variants.

The [original Omni run](../../../e2e_profiling_20260922/evidence/spark-cuda-wsl/report.json) used Spark-X2.5-4B BF16 on the RTX 5090 Laptop under WSL2, with greedy sampling, 128 output tokens, `max_model_len=4096`, `max_num_seqs=4`, `max_num_batched_tokens=512`, eager execution, disabled prefix caching and a 2.81 GiB KV pool. It measured 20 requests per prompt/concurrency group. For the identical medium and long prompts, the default output was stable at concurrency 1; one of two batch slots took another sequence at concurrency 2, and one of four slots did so at concurrency 4. The new [direct vLLM probe](../../../../experiments/probe_spark_cuda_batch_reference.py) reused the exact engine kwargs and verified the prior weight aggregate hash before loading. It generated one batch each at concurrency 1, 2 and 4 for those two prompts. Its [default report](report.json) reproduced the same token sequences and slot pattern exactly. The [audit](comparison.json), generated by [the audit script](../../../../experiments/audit_spark_cuda_batch_reference.py), verifies that every direct-vLLM result matches one of the earlier Omni outputs on the corresponding prompt and batch size.

| Gate setting | Medium, differing slots at batch 2 / 4 | Long, differing slots at batch 2 / 4 | Evidence |
| --- | --- | --- | --- |
| Default BF16 gate projection | 1 / 1 | 1 / 1 | [Direct vLLM report](report.json) |
| Existing `VLLM_OMNI_SPARK_GATE_REDUCTION=1` | 0 / 1 | 1 / 1 | [Reduction report](gate_reduction_report.json) |
| New opt-in `VLLM_OMNI_SPARK_GATE_REDUCTION=fp32` | 0 / 0 | 1 / 2 | [FP32 gate report](fp32_gate_report.json) |

The first divergent token was index 84 for medium (`flower` vs `flowers`) and index 89 for long (`and` vs `ally`). In the default direct-vLLM run, the selected token's top-two log-probability gap at these positions ranged from **0 to 0.40625** across slots; several were within **0.03125–0.046875**. The opt-in gate changes these gaps and occasionally which batch slot takes the alternative. Thus gate arithmetic contributes to sensitivity but is not the sole cause. The FP32 option remains a diagnostic setting, not a qualified default: only six direct-vLLM batches were run, not Omni's full request profile, and there was no independent task-quality or speed/energy acceptance check. Single ordered run times in the raw reports are not comparative latency evidence.

The report pins the five model weight-file SHA-256 values, aggregate checkpoint hash, config hash, prior profile hash, runtime plan, Python interpreter and platform. It used installed vLLM 0.29.0 and the current Omni Spark model implementation; Python imported this repository through `PYTHONPATH`. The experimental FP32 gate reuses PyTorch `linear` on float32 inputs and weights; it adds no custom kernel and changes no default. The command sequence from the repository root is:

```bash
repo=/home/zhout/project/edge_infer/vllm-omni-edge
py=/home/zhout/project/edge_infer/.venvs/omni-cuda-029/bin/python
model=/home/zhout/project/edge_infer/models/Spark-X2.5-4B
prior=benchmarks/edge_harness/results/e2e_profiling_20260922/evidence/spark-cuda-wsl/report.json
out=benchmarks/edge_harness/results/e2e_expansion_20260925/evidence/spark_cuda_batch_reference
for setting in auto 1 fp32; do
  case "$setting" in
    auto) report=report.json ;;
    1) report=gate_reduction_report.json ;;
    fp32) report=fp32_gate_report.json ;;
  esac
  VLLM_OMNI_SPARK_GATE_REDUCTION="$setting" PYTHONPATH="$repo" \
    VLLM_USE_FLASHINFER_SAMPLER=0 VLLM_WSL2_ENABLE_PIN_MEMORY=1 \
    "$py" benchmarks/edge_harness/experiments/probe_spark_cuda_batch_reference.py \
      --model "$model" --prior-report "$prior" --output "$out/$report"
done
python3 benchmarks/edge_harness/experiments/audit_spark_cuda_batch_reference.py \
  --omni-report "$prior" \
  --omni-requests benchmarks/edge_harness/results/e2e_profiling_20260922/evidence/spark-cuda-wsl/requests.jsonl \
  --auto "$out/report.json" --reduction "$out/gate_reduction_report.json" \
  --fp32 "$out/fp32_gate_report.json" --output "$out/comparison.json"
```

Remaining gates are a same-checkpoint independent quality reference around the batch decision, a diagnosis of the residual long-prompt numerical path, and an Omni-level performance/reliability assessment of any proposed fix. The CUDA text route remains scoped E2E, with batch-invariant output and broad quality unqualified.
