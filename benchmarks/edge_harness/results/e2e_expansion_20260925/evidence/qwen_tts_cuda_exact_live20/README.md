# Qwen3-TTS exact-state CUDA: 20 live Omni medium streams

**Disposition (2026-09-25): scoped complete text-to-audio pass on WSL2 HX370 + RTX 5090 Laptop; zero simulated deficits in 20 measured serial medium requests.** This is the current Omni two-stage AsyncOmni path with async chunks and the exact x-vector sliding-KV decoder enabled. It uses Qwen3-TTS 0.6B CustomVoice revision 85e237c12c027371202489a0ec509ded67b5e4b5. It does not exercise the AMD NPU or qualify actual sound-device playback, broad voice quality, concurrency, or sustained 30-minute behavior.

The [raw report](report.json) identifies the imported Omni source checkout (3db15ee71829dafbef5e84a2dd0481c8008831e1), installed vLLM 0.29.0, Omni 0.29 source path, PyTorch 2.13.0+cu130, WSL2 kernel 6.18.33.2 and RTX driver 610.71. The run used existing disk/JIT caches and initialized both stages in **36.04 s**; startup is excluded from request timings. The [23 per-request records](requests.jsonl) cover one warmup, 20 serial measured medium prompts, one deliberately slow consumer and one short request after abort. Every recorded request has a unique ID, ordered finite 24 kHz PCM chunks, exactly one terminal event and nonzero audio. Both stages shut down in the [compressed raw run log](run.log.gz). Startup logged model-registry and deep_gemm import errors during discovery, but they did not prevent these requests from completing.

For the **20 measured medium** requests, nearest-rank p50/p95 complete-request wall time was **1.542/1.649 s**, TTFA **104.9/117.2 ms**, and complete audio RTF **0.194/0.200**. Output durations ranged **7.12–8.72 s**, with seven or eight chunks each. The arrival-based playback simulation found **0/20 post-startup underruns**. The slow consumer intentionally slept 0.2 s after each event and recorded one **40.6 ms** simulated deficit; it is a separate stress case. The long-request abort acknowledgement took **2.77 ms**, and a subsequent short request completed with 3.04 s of audio and no simulated deficit. The harness did not check a late-audio fence after abort.

The retained [warmup chunks](audio_chunks/) were assembled in event order, including terminal audio once. The [assembly manifest](warmup_assembly.json) verifies every chunk hash and the 8.48 s [float32 WAV](warmup.wav). Separately pinned Whisper tiny.en revision 87c7102498dcde7456f24cfd30239ca606ed9063 transcribed that **one** warmup WAV exactly (WER 0); see the [ASR report](warmup_asr.json). This is an intelligibility proxy, not listening, naturalness or speaker-similarity qualification. Measured-request PCM was not archived, so the warmup ASR result must not be generalized to all 20 outputs.

The 0.25 s [memory samples](report.json) are lower bounds: sampled process-tree RSS peaked at **7.42 GB**, device-wide NVML memory use at **12.53 GB**, and available WSL host RAM fell no lower than **25.60 GB**. During the 31.07 s measured window, 122 device-wide [GPU telemetry samples](gpu_telemetry.jsonl) observed 59→70 °C (70 °C maximum), GPU-only power p50/max **83.39/92.55 W**, and raw throttle-reason value 4. Those measurements include other processes and do not establish engine-only power or a sustained thermal limit. The [derived summary](summary.json) pins the raw-file hashes, nearest-rank calculations and scope.

This improves on the earlier [four-request exact-state smoke](../qwen_tts_cuda_exact_live/README.md) and the 2026-09-22 CUDA profile with one deficit among 180 measured requests. It does not erase that earlier deficit or establish underrun-free playback over other prompts, concurrency or long-running use. The separate [117-frame generated-code audit](../qwen_tts_cuda_incremental/README.md) establishes decoder numerical parity, but this run did not independently compare its live generated PCM against a full-decode reference. The remaining M2 gates are late-cancel fencing, real audio playback, broader speech and speaker quality, measured loading peak, concurrent traffic, and sustained memory/power/thermal behavior.
