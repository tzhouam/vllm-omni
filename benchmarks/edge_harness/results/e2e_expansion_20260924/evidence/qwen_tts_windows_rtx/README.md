# Qwen3-TTS complete-WAV Omni stage on native Windows RTX Vulkan + CPU

The pinned Qwen3-TTS 0.6B CustomVoice GGUF route now completes **scoped text-to-WAV requests** through Omni `StageRuntime`/`StagePool` and the public `AsyncOmni.generate` entrypoint on native Windows. CrispASR retains the talker, codec, code predictor and their internal state; Omni owns one-slot admission, request/epoch identity, terminal audio acknowledgement, bounded WAV validation and worker cancellation. The new discrete-GPU route selects **RTX 5090 Laptop Vulkan0** for talker/codec and pins the 432 MB code predictor to **CPU FP32**. It requires independent declared **8 GiB host-RAM and 4 GiB GPU-VRAM reservations** against 16 GiB controller ceilings for each pool. The [server logs](tts_rtx_profile20_server.log) verify actual Vulkan0 device identity and codec loading. This route does not use CUDA or the NPU; it is separate from the earlier full-model vLLM CUDA streaming profile.

The exact executable and artifacts are the same as the [earlier Radeon hybrid study](../../../e2e_expansion_20260923/evidence/qwen_tts_omni_hybrid/README.md): CrispASR v0.8.35 build `00c9e752` SHA-256 `999c6af252077195adb723b96da9ee5d3cd291dc7c7a4b32dc493ae148035529`; CustomVoice Q8_0 talker at revision `29094dcb46f19b0898616aa9aeb876aa9aa6e086` SHA-256 `5227dcbc4df7c5533341d111cc469fa491a48e722b23dd10f553181b52dff2d9`; F16 codec at revision `344e279551177654762e5c7d39e217834325f222` SHA-256 `70dc95dbfdd9aa5d9d406236ff771d061bf17b0cda02a72513953355606e719b`; cached punctuation GGUF SHA-256 `faf4a43e3135bc307a66194685af00f756e6f4c28c7d9e2dd8f3517cddca5c45`, upstream revision not recorded. Weights and binary remain in local storage outside Git. The converter's original source-checkpoint revision and full same-checkpoint numerical parity remain unestablished. [Hardware record](hardware.json): Windows 11 build 26200, Ryzen AI 9 HX 370, RTX driver `32.0.16.1071`, Performance power scheme; the Radeon 890M was present but not selected.

The two named requests produced finite, nonsilent 24 kHz mono PCM: “Hello from the local computer.” returned **65,280 frames (2.72 s)**, PCM SHA-256 `d3d071531e2574b933c8acf18e2a0344c8961493bd17c63662307270a99d265c`; “The blue car is parked beside the library.” returned **76,800 frames (3.20 s)**, PCM SHA-256 `91d66409f7b3e0c5bdaa45e2091b60b8e1c3cdd64c3909d1a7878f2e9de0043f`. One excluded warmup plus **20/20 serial** complete requests for the first sentence had identical PCM, nearest-rank request-wall p50/p95 **3.153/3.231 s** (RTF **1.16/1.19**), excluding 4.016 s server/stage startup. The [raw profile](tts_rtx_profile20_report.json) retains all samples and the [first measured WAV](tts_rtx_profile20.wav). The [smoke WAV](tts_rtx_smoke.wav) was independently transcribed by pinned Whisper tiny.en as the exact first sentence, WER 0 in the [ASR record](tts_rtx_smoke_asr.json). That is an intelligibility proxy, not speaker or perceptual quality. The RTX PCM differs from the Radeon hybrid PCM (2.72 versus 2.56 s for the first sentence); there is no same-output speedup claim.

The [public AsyncOmni report](tts_rtx_public_report.json) returned one terminal audio event with the same 65,280-frame PCM hash. The profile waited until the owned server logged a new TTS prefill before aborting; no stale output remained, the worker exited and both RAM reservations cleared. A fresh stage with the same artifacts and placement used a new worker generation and returned the identical first PCM with no late output. The [3 GiB GPU-VRAM refusal](tts_rtx_refused_3gib.json) happened **before server launch** because the declared weights plus 2 GiB GPU workspace/headroom exceeded that reservation; the ledger returned to zero. A one-request [Radeon regression](tts_radeon_regression_report.json) still returned the historical Radeon PCM hash, completed cancellation/restart and reserved only shared host RAM. The [auditor](audit_report.json) checks output hashes, placement logs, p50/p95, public output, refusal and both restart ledgers.

After tightening the backend to require a GPU pool distinct from host RAM and at least 2 GiB of declared GPU overhead, a further [RTX one-request check](tts_rtx_postguard_report.json) still returned the same PCM and cleared both reservations. Its [server log](tts_rtx_postguard_server.log) again verifies RTX Vulkan0 placement. The earlier 20-request timing was not repeated for this admission-only guard change.

Reproduce using [the stage probe](../../../../experiments/probe_omni_crisp_tts.py) on native Windows Python/vLLM 0.29 with this checkout on `PYTHONPATH`, `PYTHONUTF8=1`, and `VLLM_ENABLE_V1_MULTIPROCESSING=0`. Supply the four pinned local artifacts and hashes, `--expected-gpu-name "NVIDIA GeForce RTX 5090 Laptop GPU" --ggml-vk-visible-devices 0 --gpu-capacity-gib 16 --gpu-reserve-gib 4`, the output paths, and `--warmups 1 --repeats 20 --abort-check --restart-check`. The [public probe](../../../../experiments/probe_omni_crisp_tts_entrypoint.py) uses the same placement and exact expected PCM. [The admission probe](../../../../experiments/probe_crisp_tts_rtx_admission.py) verifies a 3 GiB GPU reservation is rejected. Run [the auditor](../../../../experiments/audit_qwen_tts_windows_rtx.py) on this evidence directory.

This is a complete-WAV path with a fresh-stage recovery check. It does **not** establish incremental playable speech, RTF below 1, a measured GPU-memory loading peak, broader voice quality, concurrent requests, or an underrun-free sustained run. The earlier CUDA 30-minute findings remain a separate model/runtime route; neither this Vulkan profile nor the Radeon profile qualifies mobile/NPU joint execution.
