# Qwen3.8-27B NVFP4 native Windows RTX startup attempt

## FP8/Triton recovery on the same Windows RTX

The separate official Qwen/Qwen3.8-27B-FP8 checkpoint at revision `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a` now passes scoped complete text and image-to-text requests through this checkout's one-stage Omni pipeline on native Windows 11 build 26200 and RTX 5090 Laptop. It uses the installed vLLM 0.29.0+cu134 wheel, PyTorch 2.13.0+cu130, Triton 3.8.0, driver 610.71, explicit `linear_backend=triton`, BF16 compute, 12 GiB CPU parameter offload, 0.80 GPU-memory utilization, one sequence, eager execution and a 512-token context. The image is a synthetic 96×96 red square; the text prompt asks for the single word “ready.” This is a distinct FP8 artifact and backend, not a repair of the NVFP4 Marlin/PTX path below.

The [single image pass](qwen38_image_fp8_triton_ntfs_attempt1.json) answered `Red`; the [serial profile](qwen38_fp8_triton_ntfs_profile20.json) answered `Red` on 20/20 measured image requests and `ready` on 20/20 measured text requests. There was one unmeasured request of each type. Nearest-rank complete-request wall p50/p95 was **4.184/4.380 s for image** and **3.070/3.214 s for text**, concurrency one. The profile's engine initialization was 87.37 s, including 31.35 s reported weight loading; neither startup nor warmups are included in the request percentiles. The worker log selected `TritonFp8BlockScaledMMKernel`, loaded all 66 safetensors files, reported 16.36 GiB GPU model-load allocation and initialized a 1,974-token GPU KV cache. The 16.36 GiB value is the runner's model-load allocation, not a total GPU or host loading peak; sustained power and thermal behavior were not measured.

The checkpoint was copied from its WSL model root to native NTFS for the successful runs. Source and copy have the same 81 file names and sizes. A [full CRC32 record](fp8_copy_integrity.json) of the native copy against the bundled manifest matched all 66 safetensors and 8 other listed files. Three non-weight metadata files (`chat_template.jinja`, `generation_config.json`, `tokenizer_config.json`) differ from that manifest but have identical CRC32 values in source and copy; the manifest is stale for those files. The checkpoint revision comes from the Hugging Face download metadata, whose 81 recorded files all name the same commit. These checks do not substitute for a broad numerical or task-quality evaluation.

The retained failures delimit the fix. The [default FP8/CUTLASS load](qwen38_image_fp8_attempt1.driver.log) reached a model startup operation but the Windows wheel had no compiled `cutlass_scaled_mm` for SM120. A [small Triton FP8 block probe](fp8_triton_probe.json) passed on SM120 with the expected value 128. The [first full Triton attempt](qwen38_image_fp8_triton_attempt1.json) exposed Omni's missing structured owner for `linear_backend`; the current config projection now carries that vLLM option, with a focused test. The [next attempt](qwen38_image_fp8_triton_attempt2.driver.log) loaded all 66 weights but vLLM refused the 0.75 GPU-memory cap: 0.22 GiB available for KV versus 0.33 GiB required for a 512-token request. Raising the cap to 0.80 admitted the successful run. The [FP8 auditor](fp8_audit_report.json) checks all raw reports, failure strings, successful kernel/load/cache evidence, per-request outputs, sample counts and percentile math.

A separate [public AsyncOmni request](qwen38_fp8_public_async.json) returned `ready` for text and `Red` for the same synthetic image. Both public calls emitted cumulative text once with `finished=False` and again with `finished=True` in the later [cancellation/recovery run](qwen38_fp8_public_async_abort_recovery.json); consumers must use the completion flag rather than treating both as independent answers. The recovery run submitted a long 256-token text request, observed the task active before abort, then received exactly one finished output with `finish_reason=abort` after abort completed. The request state cleared and a fresh text request on the **same engine** returned `ready`. The earlier [count-only](qwen38_fp8_public_async_abort.json), [timestamped](qwen38_fp8_public_async_abort_timed.json) and [empty-only terminal](qwen38_fp8_public_async_abort_terminal.json) probes failed their own assertions because they treated Omni's documented terminal abort marker, which may retain partial text, as a late model answer. Their raw records are retained. This validates public request and same-engine state recovery but does not prove a server-started cancellation timing boundary or separate-stage restart.

This advances the native Windows RTX × Qwen3.8 cell to a scoped complete text/image path with public AsyncOmni and same-engine abort/recovery. It does not establish a qualified long context, video path, reference-quality suite, explicit Omni host/VRAM loading-peak admission, server-started cancellation boundary, concurrency scaling or sustained power and thermal behavior. The NVFP4 failure remains a separate unresolved artifact/runtime combination.

The pinned Qwen3.8-27B NVFP4 checkpoint, revision `dbb8f445b3145f8a4c18ddc769f032d57d32867c`, was attempted through the current Omni/vLLM 0.29 one-stage pipeline on native Windows 11 build 26200. The bounded image-to-text case used a synthetic 96×96 red image, 512-token context, one sequence, 16 output tokens, eager execution, 0.85 GPU-memory utilization and an explicit 2 GiB CPU offload. This is the same scoped case that [completed on WSL RTX](../../../e2e_recovery_20260923/README.md); Windows **did not reach inference**. No output or latency is claimed for this cell.

The [first attempt report](qwen38_image_unc_attempt1.json) records an engine-start failure after model load but its console output was not retained. The [second attempt report](qwen38_image_unc_attempt2.json) and [full driver/worker log](qwen38_image_unc_attempt2.driver.log) retain the root cause. All **three safetensors shards completed loading**, then vLLM failed while preparing NVFP4 Marlin weights: `process_weights_after_loading` → `prepare_fp4_layer_for_marlin` → `marlin_permute_scales` raised `torch.AcceleratorError: CUDA error: the provided PTX was compiled with an unsupported toolchain`. The [auditor](audit_report.json) checks the two reports, captured stack, hardware versions and source-file hashes. The probe now exits nonzero after writing a failed report, so automation cannot mistake this startup error for a successful image request.

The [hardware/runtime record](hardware_runtime.json) identifies RTX 5090 Laptop driver **610.71**, CUDA UMD **13.3**, local CUDA toolkit **13.4.59**, PyTorch **2.13.0+cu130**, and the installed native vLLM **0.29.0+cu134** wheel. NVIDIA maps CUDA 13.4 to driver branch R615, while CUDA 13.3 maps to R610 in its [CUDA release notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/). Its [minor-version compatibility guidance](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html) says applications requiring PTX JIT can fail on an older driver. The version combination and exact PTX error make this a **likely driver/toolchain mismatch**, but no R615 control has run, so the cause is not proven by an A/B driver test. This does not establish that Qwen3.8 or native Windows is intrinsically unsupported.

Capture stdout/stderr: the parent report alone omits the nested worker root cause. Run [the auditor](../../../../experiments/audit_qwen38_windows_attempt.py) on this evidence directory. Next, use an R615-or-later compatible display driver or a vLLM wheel/toolchain whose PTX is supported by R610, then rerun the exact text and image cases with placement, admission, cancellation and memory evidence. A Windows driver change is system-wide and may require a reboot; neither route has been applied in this record.
