# Spark-X2.5 GGUF through Omni on native Windows RTX 5090 Laptop

The pinned Spark-X2.5-1.7B Q4_K_M GGUF completed a **scoped text-request workload** through Omni `StageRuntime`/`StagePool` and the existing `external.llamacpp.text.v1` backend on native Windows. llama.cpp retained the model, KV and sampling; Omni provided one-slot admission, request/epoch identity, a 4 GiB host-RAM reservation, terminal acknowledgement and cancellation drain. The [raw server log](spark_rtx_server.log) identifies **Vulkan0 as NVIDIA GeForce RTX 5090 Laptop GPU**, reports **29/29 layers offloaded**, and records a 1051.02 MiB Vulkan0 model buffer. This is a GGUF/Vulkan route, separate from the earlier **Spark 4B BF16 vLLM CUDA** profile; their timings are not comparable as an acceleration study.

The exact GGUF and llama.cpp b11124 binary are the same hashed artifacts used by the [native Windows CPU/Radeon study](../../../e2e_expansion_20260923/evidence/spark_omni_llamacpp/README.md): model SHA-256 `902bde2522394954ac17821b3e5fd0df02defbc6944f122253f2580acf0503f4`; server SHA-256 `9ffc5919acb4cb43c7be5f3053b59014cce70a87d3a801fcad49c4f459984f52`. The model is 1.7B Q4_K_M at XHToken revision `1f7fa33b1245c14730da39e125714ad3a327901b`. The binary is llama.cpp b11124 build `1a679828f`. Both were checked by hash before launch and remain in local model storage outside Git.

On Windows 11 build 26200 with Ryzen AI 9 HX 370, RTX driver `32.0.16.1071` and `Performance` power scheme, the named short and 120-item inventory prompts returned `Paris` and `1511`. One excluded warmup plus **20/20 serial** inventory requests answered `1511`; nearest-rank complete-request wall p50/p95 was **0.294/0.302 s**, excluding 4.319 s initial stage startup. The prompt was 2,463 tokens and returned five completion tokens. This is complete-request wall timing, not TTFT or streamed token speed. The [stage report](spark_rtx_report.json) retains each request and the execution plan; [hardware data](hardware.json) was captured after the run. A separate [public `AsyncOmni.generate` request](spark_rtx_public_report.json) returned `Paris` on the same RTX placement, confirmed by its [server log](spark_rtx_public_server.log). The public request used the BF16 checkpoint directory only for HF config/pipeline resolution; the GGUF weights executed.

The stage refused an over-context prompt before silent truncation and recovered to answer `Paris`. It then submitted a long inventory request and waited until the owned server logged a new processing task before cancellation. The worker exited with no stale output or host-RAM reservation. A **fresh** `StageRuntime` loaded the same artifact on RTX Vulkan0 under a different worker generation and answered `Paris` without late output. Its separate [restart log](spark_rtx_server_restart.log) again records 29/29 layer offload. The [auditor](audit_report.json) checks raw logs, placement, all 20 answers, cancellation/restart and the public output. The declared 4 GiB host-RAM reservation includes model/workspace/headroom; it is not a measured load peak or an explicit GPU-VRAM admission gate.

Reproduce with [the stage probe](../../../../experiments/probe_omni_llamacpp_spark.py) on native Windows Python/vLLM 0.29 with this checkout on `PYTHONPATH`, `PYTHONUTF8=1`, and `VLLM_ENABLE_V1_MULTIPROCESSING=0`. Supply the pinned local model/server files and hashes, `--device Vulkan0 --expected-device-name "NVIDIA GeForce RTX 5090 Laptop GPU" --ggml-vk-visible-devices 0`, the output paths, and `--warmups 1 --repeats 20 --context-check --abort-check --restart-check`. The [public API probe](../../../../experiments/probe_omni_llamacpp_entrypoint.py) additionally used the real Spark BF16 config directory for resolution. Run [the auditor](../../../../experiments/audit_spark_windows_restart.py) with `--routes rtx` on this evidence directory.

This evidence qualifies only the named serial text workload and one fresh-stage recovery. Incremental token streaming, automatic same-stage restart, broad quality/token parity, concurrency, loading/GPU-memory peaks and sustained power/thermal behavior remain open. No NPU or Radeon participated in this route.
