# InternVLA Cosmos encoder on HX370 AMD NPU (2026-09-24)

**Disposition: full FP32 encoder compilation failed; an isolated A16W8 stage executed on NPU but failed numerics; NOT E2E.** This is the real Place_Markpen Cosmos CI8x8 image-encoder component, not the action policy or a device-local Omni request. The initial candidate was the unchanged FP32 ONNX export, distinct from the earlier A16W8 QDQ candidates in the [prior study](../../../e2e_expansion_20260923/evidence/internvla_cosmos_amd_npu/README.md). The bounded stage and quantization controls follow below.

The 502,735-byte ONNX graph has SHA-256 `fee79864e393df35475ba243e14b4995c5651aa33e7e182cd1fda726425668b7`; its 124,649,472-byte external weight data has SHA-256 `b9bc3411c10f05daec2ff977698ee100979ef756ed7f0d685275403517558b58`. The fixed `[6,3,256,256]` ramp and pattern fixtures have SHA-256 `dcbaf1391ca914d4bbccc1cb384daf05666e771d9cdae90c4f069ec8fcf05368`. These artifacts are retained outside Git under `/home/zhout/project/edge_infer/models/InternVLA-cosmos-onnx/`.

On HX370 native Windows 11 build 26200, AMD NPU driver `32.0.203.329`, ONNX Runtime `1.30.0`, ONNX `1.22.0`, and VitisAI EP `1.8.63.0`, the [CPU control](cpu_control.json) returned `[6,16,32,32]` latents within `8.737078e-7` and `2.286713e-6` relative L2 of the retained source on ramp and pattern. The CPU-control report calls the candidate `quantized` because the probe's candidate argument has that generic name; the file passed here is the **same FP32 source**, with no QDQ conversion.

With the same graph and fixtures, VitisAI session creation aborted at a native LLVM `SmallVector.h:291` assertion (`idx < size()`), process exit code **3**. The [raw mixed-encoding log](npu_probe.log), SHA-256 `0f48cf84b5b528d193931a99bb5e594bf792d7040cded1b5f0d8bc79ed1e2de5`, records the failure. No inference JSON was produced; the only emitted [profile file](npu_probe_profile_2026-09-24_20-32-05_385.json) is zero bytes, with no execution event or placement evidence. [AMD's VitisAI documentation](https://ryzenai.docs.amd.com/projects/WinML/en/latest/model_support.html) describes automatic BF16 handling of FP32 models; this run did not reach a profile from which internal precision can be confirmed.

The [probe](../../../../experiments/probe_internvla_cosmos_amd_npu.py) checked exact model, weights, fixture and prior-export hashes before the provider attempt. This result constrains this FP32 export with EP `1.8.63.0`; it does not show that the encoder or model is generally unsupported on AMD NPU. The prefix bisection below narrows the failing graph boundary.

## Real-weight prefix bisection

The [prefix extractor and probe](../../../../experiments/bisect_internvla_cosmos_vitisai.py) pins the same source graph, external weights and pattern fixture. Cut 147 ends at `Conv`, cut 148 at the first `GroupNormalization`, and cut 149 at its `Sigmoid`. All three passed CPU inference and created VitisAI sessions, but their profiles contain **only CPU node events** (39/68/69 respectively), with output bitwise equal to CPU. Their [extraction reports](prefix147_extract.json), [probe reports](prefix148_probe.json), and raw profiles are retained here. Adding cut 150, the first `Mul(group_norm, sigmoid)`, reproduced the native `SmallVector.h:291` abort before any inference or NPU event; [the cut-150 report](prefix150_probe.json) records the pre-crash state. This is an observed graph boundary, not proof that `Mul` alone is defective.

The [SiLU rewrite](../../../../experiments/rewrite_internvla_silu.py) expressed that activation as `x/(1+exp(-x))`. It preserved CPU output within `6.53e-8` relative L2 across both fixtures ([rewrite report](prefix150_silu_rewrite.json)), but VitisAI still aborted during session creation ([raw log](prefix150_silu_probe.log)). The previously documented unvectorized VitisAI configuration also left the original cut-150 graph crashing ([control report](prefix150_unvectorized_probe.json)).

The [first-GroupNormalization decomposition](../../../../experiments/rewrite_internvla_groupnorm.py) uses fixed `[6,32,4,64,64]` grouping, standard reductions and the original affine weights. It preserved CPU output within `9.98e-6` relative L2 on cut 150 and `4.71e-6` on cut 151, which includes the following convolution. Both rewritten prefixes created VitisAI sessions without a native abort, but their [cut-150](prefix150_groupnorm_probe.json) and [cut-151](prefix151_groupnorm_probe.json) placement profiles contain **only CPU node events** (51 and 54). Thus the rewrite resolves this compiler crash for the bounded prefixes but does not provide NPU execution or a useful accelerated stage. Neither rewrite has been applied to the full encoder. The next experiment needs a provider-compatible NPU partition with numerical and action-output checks; a CPU-only run cannot qualify the AMD NPU cell.

## Quantized prefix controls

The [QDQ calibration probe](../../../../experiments/quantize_internvla_cosmos_prefix.py) used the same two pinned fixtures and original real weights on the decomposed cut-151 prefix. Quantizing all 14 prefix convolutions as A8W8 gave CPU-output relative L2 **4.104%/2.884%** on ramp/pattern ([report](prefix151_groupnorm_a8w8_quantization.json)); quantizing only the final `node_conv2d_13` as A8W8 still gave **3.880%/2.528%** ([report](prefix151_groupnorm_a8w8_conv13_quantization.json)). Both fail the provisional 1% component gate, so their NPU paths were not used for a support or timing claim. Calibration on two synthetic fixtures is not representative task calibration.

The same single-convolution candidate with A16W8 preserved cut-151 CPU output within **0.619%/0.529%** relative L2 ([quantization report](prefix151_groupnorm_a16w8_conv13_quantization.json)). Its [VitisAI placement probe](prefix151_groupnorm_a16w8_conv13_probe.json) created a session in 28.99 s and returned the same output as its ORT CPU candidate, but all **58** profiled node events were `CPUExecutionProvider`; no NPU node executed. Its one 50.96 ms inference is a mixed provider invocation timing with CPU execution, not an NPU speed result. This candidate is numerically promising for the bounded prefix but does not qualify even an NPU component. The complete encoder and action policy remain untested with these rewrites.

## Explicit real-activation stage boundary

The [boundary preparation/probe](../../../../experiments/probe_internvla_cosmos_boundary.py) extracted the original real-weight `Sigmoid → Mul → Conv` nodes after the first GroupNormalization. It generated two CPU activations from the pinned pixel fixtures with the original cut-148 prefix and checked that the isolated CPU output exactly reproduces the original cut-151 prefix on both inputs ([preparation report](gn_to_conv13_prepare.json)). The 6,668,907-byte paired activation fixture is retained outside Git with SHA-256 `7bca8b4dcafa0ab0d45387e95a4d3e844f04f296f9253a4d4ac54ab5682d068c`; the extracted FP32 ONNX SHA-256 is `ff2ebad2c59a472b561536fa49cdd8bc43cf8e7bcf000a8ff4420f8e3a4766c8`. This stage is a diagnostic boundary: moving a `[6,128,64,64]` activation between backends has not been justified by end-to-end cost or memory evidence.

The isolated [FP32 VitisAI probe](gn_to_conv13_fp32_probe.json) created a session but ran all four profiled nodes on CPU. The [A16W8 per-channel QDQ candidate](gn_to_conv13_a16w8_quantization.json) passed its bounded CPU gate at **0.619%/0.529%** relative L2 on ramp/pattern, matching the prefix candidate. Its [VitisAI probe](gn_to_conv13_a16w8_paired_probe.json) ran **one actual VitisAI node** and three CPU nodes on the pattern fixture. The output was finite, but **4.4948 relative L2**, cosine **−0.0033**, and maximum absolute difference **18.27** versus the same quantized candidate on ORT CPU. This is a placed but **numerically failed** component, not qualified InternVLA support. The paired 6×256×64×64 CPU/NPU tensors are retained outside Git with SHA-256 `c108accf75ac895dccfc873e626c6de14c93a8f45855949e9be5ef67be6e89f7`. The [layout analysis](gn_to_conv13_a16w8_layout_analysis.json) found no recovery from simple NHWC, height/width, channel reversal or 16/32-channel block permutations; it does not rule out other input-layout or compiler defects.

The previously used unvectorized VitisAI config caused [session creation to abort](gn_to_conv13_a16w8_unvectorized_probe.log) with `Target auto-discovery: target proto not found for target: X2`; its profile file is empty and it produced no output tensor or placement comparison. A [per-tensor A16W8 weight variant](gn_to_conv13_a16w8_pertensor_quantization.json) missed the provisional CPU gate at 2.131%/1.709% relative L2 and was not advanced to NPU. The original FP32 boundary converted to ONNX opset 17 with exact CPU parity, but its [VitisAI profile](gn_to_conv13_fp32_opset17_probe.json) still contained only CPU nodes. The A16W8 graph could not be converted to opset 17: ONNX's converter [rejected UINT16 QuantizeLinear](gn_to_conv13_a16w8_opset17_conversion.log) at opset 20. None of these controls repairs the numerical failure or supports a full encoder/policy route.
