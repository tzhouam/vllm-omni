# Qwen3.8-27B GGUF on WSL CPU

The same pinned [ggml-org/Qwen3.8-27B-GGUF](https://huggingface.co/ggml-org/Qwen3.8-27B-GGUF) Q4_K_M language model and Q8_0 vision projector as the [native Windows CPU run](../qwen38_gguf_windows_cpu/README.md) passed bounded complete text and image-to-text requests through Omni `StageRuntime` on WSL2 Ubuntu 26.04. The exact checkpoint revision is `efbb3b1f70a21d97fd4495240648405f7228554f`. The local Linux CPU-only llama.cpp server was b10849, commit `e71b80510`, SHA256 `0d6bb6ade8da8f3231917ce23261da5331333df0007dc4bda74c00e0774e092c`, loaded by the current checkout with installed vLLM 0.29.0. [Hardware/runtime record](hardware_runtime.json).

The WSL RAM quota is 30.91 GiB. Two [pre-admission](smoke.json) [attempts](smoke2.json) refused a 28 GiB reservation when available RAM after Python imports was below it. A [27 GiB attempt](smoke3.json) loaded the model but was correctly refused because its CPU-repacked process RSS exceeded that reservation. The explicit `--no-repack` option removed the 9,180 MiB repack buffer without changing weights or precision. A [24 GiB smoke](smoke4.json) then passed `ready` text and `Red` synthetic-image answers; the stage measured 20,026,560,512 bytes of loaded process RSS, verified `CPU_Mapped` model storage and `CLIP using CPU backend`, and fully released the reservation. The CPU-only build emits `warning: no usable GPU found` rather than an offload-count line, so the backend requires positive CPU-buffer evidence before labeling CPU placement.

The [serial profile](profile20.json) used one 2048-token slot, a 128-token maximum output, deterministic temperature zero, a 96×96 solid-red PNG, and short prompts requesting `ready` and `Red`. After one warmup of each type, **20/20 text** and **20/20 image** requests returned the expected two-token answers. Nearest-rank complete-request p50/p95 was **1.934/1.983 s text** and **3.642/3.789 s image**, concurrency one. Startup was 11.45 s on this run and is excluded from those percentiles; the earlier smoke startup was 25.01 s, so cache state should be treated as uncontrolled. The [server log](profile20.server.log) and [auditor](audit_report.json) verify hashes, CPU model/vision placement, every output and terminal epoch, percentile arithmetic and ledger release.

Reproduce with [the Omni probe](../../../../experiments/probe_omni_llamacpp_qwen38.py), the checkpoint hashes in the Windows CPU record, `--device cpu --reserve-gib 24 --no-repack --repeats 20`, the Linux server hash above, and fresh log/report paths. Use the vLLM 0.29 environment, `PYTHONPATH` pointing to this checkout, `LD_LIBRARY_PATH` pointing to the llama.cpp build directory, `CUDA_VISIBLE_DEVICES=''`, and `VLLM_ENABLE_V1_MULTIPROCESSING=0`. Run [the auditor](../../../../experiments/audit_qwen38_gguf_wsl.py) against this evidence directory. This is scoped P-level evidence for short text and one synthetic image, not long-context or broad visual quality, public AsyncOmni, cancellation/restart, concurrent serving, loading/request memory peaks or sustained power and thermal behavior. The WSL quota and no-repack setting differ from native Windows, so their latencies are not a paired OS comparison.
